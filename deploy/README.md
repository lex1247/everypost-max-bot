# EveryPost: постоянный сервер для существующих MAX и Telegram

Это развёртывание существующего проекта `lex1247/everypost-max-bot`. MAX берётся из ветки на основе `main`, Telegram и сборщик — из ветки на основе `telegram-posting`. Два приложения используют одну PostgreSQL 18: MAX — прежние таблицы `public`, Telegram — прежнюю схему `repost_bot`. Отдельные боты не создаются.

## Статус подготовки

18 сентября 2026 пакет развёрнут на тестовом Timeweb VPS в режиме `standby`. Проверены сборка обоих Docker-образов, восстановление свежего дампа PostgreSQL 18, доступ к API MAX и Telegram, скачивание TikTok и построение отпечатка, 300 автоматических проверок и автоматический запуск после полной перезагрузки VPS. Все 76 таблиц совпали по содержимому до и после перезагрузки. Дамп также сохранён вне VPS.

Рабочие отправители и вебхуки остаются на Render. HTTPS пока не прошёл проверку: общая бесплатная зона Timeweb исчерпала лимит Let's Encrypt. Реальная публикация с нового VPS, постоянное внешнее резервное копирование и переключение рабочей очереди ещё не выполнены. Тестовый сервер может быть удалён после окончания бонусного баланса; постоянная эксплуатация требует отдельного решения. Точные версии и результаты находятся в `../release.json`.

## Состав

- `compose.yaml`: постоянная база, два приложения и HTTPS; PostgreSQL не открыт в интернет. Перезапуск контейнеров при завершении процесса и после перезагрузки сервера.
- `monitor.py`: проверка каждую минуту; перезапуск только зависших работающих приложений, максимум 3 раза в час и не чаще раза в 5 минут. Намеренно остановленные приложения остаются остановленными. Ошибки базы, просроченные публикации, неопределённые отправки, заполнение диска и отсутствие свежего бэкапа требуют внимания владельца. Уведомления идут владельцу через существующего TG-бота при изменении состояния.
- `/health` проверяет доступность БД и работу обработчиков. Допустимые интервалы между проходами учитывают длительные обработки медиа: MAX 10/20/30 минут, TG до 30 минут. Недоступность HTTP обнаруживается быстрее.
- `backup.sh`: каждые 6 часов полная копия БД и конфигурации с шифрованием в отдельное S3. Перед загрузкой проверяется восстановление в одноразовую базу. Хранение: последние 6, дневные 7, недельные 4. Достаточность тарифа S3 контролировать по фактическому объёму.
- `preflight.py`: проверяет HTTPS, режим ожидания и скачивание одного стартового TikTok-видео с построением отпечатка. Ничего не публикует.
- Режим `standby` запрещает входящие изменения, публикацию, сбор по расписанию и регистрацию вебхуков. В нём можно безопасно проверять **отдельную копию базы**.

## Подготовка релиза

Из существующего Git checkout с обеими проверенными версиями:

```sh
python3 deploy/assemble.py --max-ref <полный-коммит-MAX> --telegram-ref <полный-коммит-TG> --output /opt/everypost
cd /opt/everypost/deploy
python3 configure.py
cp .env.example .env
```

Файлы `config/*.env` остаются только на сервере с правами 600. Заполнить имеющимися токенами и настройками из Render; не публиковать их в Git и не отправлять в чат. `configure.py` не перезаписывает существующие настройки. Проверить совпадение MAX-токена в обоих приложениях. Сохранить остальные используемые настройки Render, например аккаунт чтения Telegram и административный ID.

Нужны два действующих HTTPS-имени: `MAX_DOMAIN`, `TG_DOMAIN`; их DNS направляется на новый IP. В MAX указать `PUBLIC_URL=https://MAX_DOMAIN`, `BRIDGE_URL=https://TG_DOMAIN`; в TG — `PUBLIC_URL=https://TG_DOMAIN`. Домены `onrender.com` перенести нельзя. Подобрать технические имена провайдера или существующие имена пользователя; новый платный домен требует отдельного согласования.

Установить Docker Engine и Compose из официального репозитория для ОС сервера; включить Docker после перезагрузки. В сетевом экране открыть только HTTPS/HTTP и SSH с нужных адресов. Не отключать проверку сертификатов MAX. Нужны синхронизация часов и свободное место для временного дампа и пробного восстановления.

## Проверка до переключения

1. Получить зашифрованную/защищённую копию PostgreSQL Render 18 через `pg_dump --format=custom --no-owner --no-privileges`. Пароль передавать через закрытый файл `.pgpass` или переменную, не в аргументах команд и не в логах.
2. Запустить только `docker compose up -d db`; восстановить дамп в **пустую новую** базу с `pg_restore --exit-on-error --single-transaction --no-owner --no-privileges`. Если она уже содержит данные, остановиться и развернуть новую тестовую базу; не использовать `--clean` на рабочей базе.
3. Оставить `EP_RUN_MODE=standby`, выполнить `docker compose build` и `docker compose up -d`. Дождаться сертификатов; затем `python3 preflight.py`. Убедиться в совпадении каналов, настроек, источников, выбранных роликов и расписания.
4. Перезапустить контейнеры и сервер в standby. Повторить проверки. Проверить доступность MAX и Telegram с нового IP и загрузку медиа. Тестовая публикация возможна только в согласованный тестовый канал/по согласованной публикации.
5. Создать приватное S3, заполнить `backup.env`, один раз выполнить `docker compose --profile maintenance run --rm -T backup init`. Сохранить `RESTIC_PASSWORD` отдельно от сервера. Без него зашифрованную копию восстановить нельзя. Выполнить `bash backup.sh`, `restic check` через контейнер и восстановить пробную копию **из S3** в отдельную папку/базу. Одна загрузка не доказывает восстановимость.

## Переключение рабочей очереди

Выполнять только после успешной проверки сервера и оплаты согласованного тарифа.

1. Зафиксировать оба текущих Render-коммита, старые URL и количество/ID ожидающих постов. Выбрать промежуток между публикациями. Остановить обработку и оба сервиса Render; проверить отсутствие выполняющихся отправок. Неопределённую отправку сначала сверить с каналом.
2. Снять **свежий финальный дамп после остановки старых обработчиков**. Не использовать прежний тестовый снимок как финальный.
3. Остановить приложения на новом сервере. Восстановить финальный дамп в новую пустую БД, переключить `DATABASE_URL` обоих приложений на неё. Проверить ID, даты, статусы, настройки, последовательности ID и связность таблиц; прежнюю тестовую БД сохранить отдельно до завершения.
4. В `.env` поставить `EP_RUN_MODE=active`, выполнить `docker compose up -d --force-recreate max telegram edge`. Проверить оба `/health`, регистрацию новых вебхуков, связь с обработчиком контента и путь мини-приложения `/calendar` в настройках MAX-бота. Проверить список подписок MAX и убрать старую подписку Render после подтверждения новой. Обновить старые ссылки в меню/настройках ботов.
5. Скопировать unit-файлы в `/etc/systemd/system`, выполнить `systemctl daemon-reload` и `systemctl enable --now everypost-monitor.timer everypost-backup.timer`. Сделать первый бэкап сразу.
6. Проверить реальную плановую публикацию, подпись, отсутствие повторной отправки, поступление новых кандидатов и резервный TG→MAX. Затем проверять несколько суток работы без компьютера пользователя. Полный простой VPS требует **внешней** проверки доступности; локальный монитор сам об исчезновении своего сервера сообщить не может. Внешний монитор подключить отдельно и проверить доставку тревоги владельцу.

Откат после новых публикаций нельзя делать простым запуском старой копии Render: она может отправить уже опубликованное повторно. Сначала остановить нового отправителя, сохранить актуальную базу, сверить спорные отправки; запускать прежнюю версию приложения только с актуальным состоянием базы.

## Границы резервного копирования

Сохраняются база, настройки, токены вложений и источники. Исходные медиа остаются на платформах; это не бессрочный архив видеофайлов. S3-ключи и ключ расшифровки должны храниться у владельца вне VPS. При заполнении тарифа остановиться/очистить по согласованному сроку хранения, а не автоматически покупать расширение.

## Проверки

```sh
node --test max/runtime-tests.mjs
PYTHONPATH=telegram python3 -m unittest discover -s telegram -p 'test_*.py'
python3 -m unittest discover -s deploy -p 'test_*.py'
```

Дополнительно выполняются существующие проверки MAX: подборка, очередь, права и подписки. Регрессионные тесты не отправляют настоящие посты.
