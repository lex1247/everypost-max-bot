# Отдельный бесплатный Render-сервис EveryPost

## Что создаётся

Ветка `telegram-posting` в репозитории владельца `lex1247/everypost-max-bot`, затем один web service `everypost-telegram-bot`, регион Oregon, тип экземпляра Free. Сервис `everypost-max-bot` продолжает работать со своей веткой `main` и своим MAX webhook.

Blueprint не объявляет существующую базу или MAX-сервис как управляемые ресурсы. Он только ссылается на `everypost-db.connectionString` и переменную `MAX_BOT_TOKEN` существующего сервиса. Пароль базы не нужно копировать на компьютер. Новый Python-код использует только схему `repost_bot` и один PostgreSQL-сеанс.

## Последовательность размещения

1. Загрузить только подготовленные исходные файлы в ветку `telegram-posting`. Не включать `.env`, `data/`, `work/`, сессии и ключи.
2. В Render создать Blueprint из этой ветки и файла `render.yaml`. Предварительный план должен показывать только создание одного **Free web service**, без платных ресурсов и без обновления MAX-сервиса/базы.
3. Заполнить секретные переменные нового сервиса: `TG_BOT_TOKEN`, `OWNER_ID`, случайный `MIGRATION_TOKEN` длиной не меньше 32 символов. Остальные значения и ссылки заданы Blueprint. Токен миграции передаётся только заголовком Authorization, не URL.
4. Сборка устанавливает зависимости, выполняет модульные проверки и тесты настоящей PostgreSQL в одноразовом локальном кластере. При сбое сборка останавливается. Рабочая база при этих тестах не используется.
5. Новый сервер сначала поднимает `/health`, но не принимает управление живым ботом: `REQUIRE_MIGRATION=1` удерживает обработчики до переноса состояния.
6. Остановить локальный процесс после завершения текущей отправки. Сделать согласованный снимок SQLite через `migration.export_data`. Экспорт включает источники, маршруты, курсоры, очередь, результаты доставки и редактор, если он использовался; исключает служебные настройки токенов.
7. Передать снимок JSON по HTTPS на `/migration/import`, с `Authorization: Bearer MIGRATION_TOKEN`. Импорт разрешён только в пустую схему, выполняется транзакцией и исправляет последовательности идентификаторов. Повторный импорт отклоняется.
8. Проверить ответ с количеством строк; затем вызвать `/migration/activate` с тем же заголовком. Только после этого сервер включает Telegram webhook. Старый MAX webhook не изменяется.
9. Проверить новый сервис, команду боту и одну собственную тестовую публикацию. Сохранить резервную копию локальной SQLite. После успешного переноса удалить переменную `MIGRATION_TOKEN` из нового сервиса: служебные точки входа станут недоступны.

При неудачном развёртывании до активации можно продолжить локальный запуск. После активации возврат требует сначала остановить облачный обработчик, выгрузить актуальное состояние и отключить именно Telegram webhook. Не запускайте старую SQLite-копию параллельно с облачным обработчиком.

## Free и платный переход

Free web service спит после 15 минут без входящих HTTP-запросов. Исходящие обращения к источникам не предотвращают сон. Бот просыпается от входящего сообщения; выход постов по расписанию во время сна не гарантируется. Публикации, просроченные больше чем на пять минут, остаются для проверки в черновиках.

Файлы Free эфемерны, поэтому все важные данные находятся в PostgreSQL, медиа сохраняются как Telegram file_id или проверенные ссылки. База Free истекает через 30 дней с создания. У существующей `everypost-db` в панели указан срок **8 октября 2026 года**; перед этой датой нужно отдельно обновить тариф базы или перенести данные. Создание нового сервиса срок базы не продлевает.

Позже в настройках **нового web service** выбирается платный тип экземпляра; сохраняются URL, webhook и все настройки. Отдельно обновляется тип экземпляра PostgreSQL. Старый MAX-бот и его тариф меняются только по отдельному решению владельца.
